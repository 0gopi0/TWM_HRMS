# Taste
- Prefers professional, subtle typography with slightly rounded fonts for UI, over geometric/playful sans fonts that feel "off." Confidence: 0.8
- Prefers a warm editorial serif for headlines paired with a clean professional sans for body/UI text. Confidence: 0.6
- Wants explicit, visible save-confirmation feedback on the UI: a green toast notification in the top-right corner confirming data was saved, auto-dismissing after a few seconds. Confidence: 0.9
- Open to the agent installing or activating design/vision skills (e.g., design, agent-browser) when working on visual/design tasks. Confidence: 0.7
- Delegates aesthetic/design judgment to the agent, expecting the agent to make the call ("you can be the judge of it"). Confidence: 0.6
- Wants the codebase knowledge graph (graphify) kept current/synced with the working tree after making code changes, preferring incremental updates over full rebuilds. Confidence: 0.8
- Prefers to launch both the backend and frontend dev servers with a single command from the project root (e.g., `npm run dev`), rather than starting them separately. Confidence: 0.6
- Prefers dedicated, standalone tabs/pages at the root level of the left sidebar for each distinct functional area (e.g., a separate "Approvals" entry), rather than nesting those actions inside another page. Confidence: 0.8
- Prefers a lean, focused UI: each page should surface only its primary action (e.g., the leave-request form) and omit redundant lists/tables that duplicate information shown elsewhere (e.g., the Person/Type/Dates/Status table). Confidence: 0.6
- Wants the application running on a real, persistent local MySQL/MariaDB database, not the in-memory fallback; expects the agent to be able to install/configure the DB server (e.g., user-space via mise) and wire the app to it so data survives restarts. Confidence: 0.8
- Wants self-service transparency for record creators: an applicant should see the status of their own submitted requests, and if rejected, the approver's rejection reason (comment) surfaced next to it. Confidence: 0.7
- Prefers a written, reviewable plan (plan mode) before non-trivial setup/installation work is executed, so the user can approve the approach and steps first. Confidence: 0.7
- For complex tasks, wants the agent to follow a structured workflow: analyze → plan → identify independent workstreams → delegate to sub-agents (run in parallel when independent) → keep related work in separate contexts/worktrees → review sub-agent output before integrating → run tests and fix issues before reporting completion. Explicitly NOT to use sub-agents for trivial tasks where delegation adds overhead. Confidence: 0.85
- Prefers to run the dev servers themselves in their own terminal rather than have the agent leave a background `npm run dev` instance running; the agent should stop any background dev processes cleanly so the user owns ports 4000/5173. Confidence: 0.6

Confidence: 0.7
- Finds flat, static UI cards "boring and ugly" — when they ask for a component to be made "more beautiful," they want a substantive visual redesign with polish (e.g., animated/live status indicators, hero metrics like a ticking elapsed-time value, subtle gradient tints and tone-coded states), not a minimal spacing/font tweak. Confidence: 0.7
- On the dashboard, wants secondary/history sections (e.g., "My recent leave requests") pushed all the way down to the end of the page, below the primary summary cards (today's status, leave balance) — detail/activity lists come last in the vertical flow. Confidence: 0.6
- When committing, supplies the exact commit message to use verbatim (lowercase, informal, e.g., "ppayslips option added") and expects commit + push to GitHub (origin) in one step as part of the request — no draft PR or message proposal needed. Confidence: 0.7
- Strongly reactive to visual-polish/layout issues: stretched full-width cards/sections and cramped placeholder text both read as "very ugly" to them. Expects lonely cards to get compact max-widths (no dead space), and empty/zero-state text to stay LEFT-aligned with comfortable padding (e.g., `padding: 24px 22px`) instead of hugging the card edge — they explicitly rejected centering ("the text should be left aligned") after the agent centered it; the "ugly" complaint was about cramped spacing, not alignment. When fixing "ugly" text, reach for padding/breathing room first, never text-align changes. Confidence: 0.85
- Prefers related dashboard sections placed side by side in a responsive two-column row (e.g., "My leave balance" + "My recent leave requests" in an auto-fit grid with equal card heights, stacking back to vertical on narrow screens) rather than each taking a full-width row — horizontal space should be shared, not stacked. Confidence: 0.7
- Sends UI/layout complaints as screenshots (asked whether the agent can process images, then immediately pasted one) — when a screenshot arrives, read the exact misalignments, widths, and stacking problems from it and fix those specific issues without asking clarifying questions. Confidence: 0.7
- On detail pages, wants a stacked main column — summary tiles (e.g., leave balances) and the history/list section one below another in the left column — with the form/primary-action panel pinned as a fixed-width right sidebar; grid collapses to a single column on narrow screens. Note: the initial ~360px sidebar felt too narrow to them — they explicitly asked for the Request-leave form column to be widened (now minmax(340px, 460px)). Confidence: 0.8
- Prefers compact, vertically-tight form/panel cards: when a section reads as too tall (e.g., "Request leave section… reduce height"), compress it by tightening spacing — smaller form gap (~10px instead of 14px), zero heading margins, tighter label gaps — rather than removing content or functionality. Confidence: 0.7
